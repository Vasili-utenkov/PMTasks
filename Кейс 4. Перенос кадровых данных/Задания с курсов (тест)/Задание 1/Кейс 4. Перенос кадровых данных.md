##### Контекст и цифры
Компания переходит с нескольких таблиц Excel на готовую кадровую систему. 
Нужно перенести карточки 750 сотрудников: ФИО, подразделение, должность, дату приёма, рабочий график и остаток отпуска. 
Список полей, правила заполнения и шаблон итогового отчёта согласованы с HR. 
Переход должен состояться в выходные 26–27 октября, чтобы с понедельника кадровики работали только в новой системе.
Перед запуском HR должен сверить выборку из 50 карточек, а бухгалтерия — получить отчёт по отсутствиям. 
В новом решении не должно быть карточек без подразделения или даты приёма. 
Исходные таблицы содержат персональные данные, поэтому доступ к ним есть только у согласованной группы сотрудников.
##### На что обратить внимание
Подумайте над набором стейкхолдеров.
Границы проекта: не нужно изобретать новую кадровую систему; нужно подготовить данные, правила переноса, проверку и план возврата к прежнему состоянию при ошибке.
В требованиях пригодятся проверка обязательных полей, журнал ошибок, отчёт о переносе и разграничение доступа.
##### Выбор методологии: что проверить
Какие условия здесь известны заранее: данные, поля, дата, критерии приёмки? Что важнее — постоянно менять содержание работы или пройти последовательные этапы анализа, подготовки, пробного переноса, сверки и запуска?
##### Стартовые точки для User Story
Здесь User Story могут быть не только от лица сотрудника. Например, подумайте о действиях кадровика, бухгалтера и администратора данных: проверить карточку, увидеть ошибку переноса, получить отчёт.

### Шаг 2. Сбор данных. 

==тип==  
- Перенос данных: _с нуля_
- Проверка данных, правила переноса, составление скриптов переноса: _доработка_
- Откат изменений: _сопровождение_



==состав команды== 
- _Аналитик_ : Анализ данных и разработка алгоритмов обогащения данных.
- _Backend_: Написание скриптов переноса данных. 
- _PM_: Руководство проектом. координация сроков
- _Администратор данных системы учета_: Загрузка и откат данных в целевой системе. Контроль и анализ загружаемых данных.

Если квалификация аналитика позволит создавать скрипты для заполнения БД системы учета кадров, то роли _Аналитик_ и _Backend_ можно совместить

==уровень неопределённости== 
_стабильная часть_:
- Программа ведения кадров определена
- Состав переносимых данных известен и согласован с HR
- Определены базовые правила для целостности данных
- Правила доступа к данным

_изменяемая часть_:
- Условия проверки переносимых данных могут дополняться
- Алгоритмы сверки и обогащения данных
- Скрипты переноса данных и скрипты отката

==требования заказчика==
_жесткие_:
- Срок 26–27 октября. 
- Базовые правила заполнения карточек 
- Список переносимых данных сотрудников
- Шаблон итогового отчета
- Доступ к исходным данным только по согласованию

_гибкие_:
- Алгоритмы сверки и обогащения данных
- Скрипты переноса данных сотрудников из таблиц Excel
- Скрипты заполнения данных для одного сотрудника
- Скрипты отката данных


### Шаг 3. Выбор методологии. 
_Waterfall_: На основной поток работ: очистка данных, внесение данных в новую систему, проверка данных
_Kanban_: Откат всех данных при возникновении критической ошибки переноса данных
_Scrum_: Составление скриптов миграции: выявление групп пользователей с одинаковым набором (или частичного отсутствия) данных и работа обогащению данных и маппингу. Каждому скрипту переноса групп карточек сотрудников создается скрипт отката переноса. 
_Kanban_: Перенос одиночных карт сотрудников. Каждому скрипту переноса карточки сотрудника создается скрипт отката переноса

### Шаг 4. Инициация проекта. 
==Название и описание проекта==. 
_Перевод системы учета кадров в новую систему_
Перенос карточек 750 сотрудников из Excel в целевую систему кадрового учета. Работы включают в себя очистку  и обогащение данных. Шаблоны и состав полей переносимых карт согласован. Заданы критические требования к составу данных, требующихся для переноса в целевую систему. Доступ к данным только у согласованной группы сотрудников. Цель проекта - переход с 28 октября на ведение кадрового учета в новой системе.


==Цели проекта==. 
- 26-27 октября перенести и проверить все 750 карточек сотрудников в новую кадровую систему. Проверяется актом приемосдаточных работ
- К утру понедельника составить бухгалтерии отчет по карточкам сотрудников, не прошедших миграцию
- Обеспечить, чтобы к моменту завершения переноса данных, процент карточек сотрудников, отправленных на ручной разбор, не должен превышать 2%

==Ограничения и допущения==. 
_Ограничения_
- Миграция должна быть проведена в выходные 26–27 октября
- Определена целевая система кадрового учета
- Определен список полей карточек для переноса и правила их заполнения
- Определены критерии целостности данных
- Определен шаблон итогового отчета по миграции

_Допущения_
 - Сотрудники HR будут доступны для проверки данных
 - Бухгалтерия предоставит недостающие данные
 - Исходные данные в Excel будут доступны и будут заблокированы на изменения на период миграции данных
 - Целевая система готова принять данные по согласованному шаблону
 - В период миграции не будет сбоев инфраструктуры
 - Сотрудник СБ проверяет формируемые в ходе выполнения работ отчеты на содержание в них чувствительных или критичных данных


==Критерии успеха==.  
- Успешная сверка данных: HR должен сверить выборку из 50 карточек
- Целостность данных подтверждена актом приемо-сдаточных работ
- Составление для бухгалтерии списка сотрудников.
- Процент не перенесенных данных не превышает целевой параметр
- С понедельника работа ведется в целевой системе. Откат данных не понадобился


### Шаг 5. Формирование бэклога. 

US-001. Как _HR_ я хочу _получить выборку из 50 случайных карточек, прошедших миграцию_ что бы _убедиться в точности переноса_
Acceptance Criteria
- Получено 50 случайных карточек
- В выборке нет карточек с расхождениями
Приоритезация: _Must have_


US-002. Как _HR_ я хочу _получить список карточек с недостающими данными_ что бы _дополнить их до переноса_
Acceptance Criteria
- Получен список карточек с недостающими данными 
- Данные дополняются вручную сотрудниками HR и бухгалтерии
- Повторная выборка не выявляет карточки с недостающими данными
Приоритезация: _Must have_


US-003. Как _HR_ я хочу _видеть списки дубликатов карточек_ что бы _устранить их перед миграцией_
Acceptance Criteria
- Выбираются записи, в которых присутствуют дубликаты карточек. Условия выборок могут меняться
- Карты проверяются. При признании дубликата ставится специальная пометка, запрещающая миграцию
- Повторная выборка не выявляет дубликатов карточек
Приоритезация: _Should have_


US-004. Как _PM_ я хочу _иметь скрипты отката_ что бы _минимизировать риски при критической ошибке миграции или для корректного тестирования_
Acceptance Criteria
 - Каждому скрипту по переносу данных соответствует свой скрипт отката
 - Запуск скрипта отката  корректно удаляет вставленные в целевую систему данные
Приоритезация: _Must have_


US-005. Как _PM_ я хочу _получить сводный отчет по миграции_ что бы _предоставить его к акту приема работ_
Acceptance Criteria
- Отчет может формироваться в любой момент 
- Отчет показывает исходное количество карточек в Excel, количество мигрированных карточек, дублей, карточек с неполными данными
- Исходное количество карточек должно совпадать с количеством мигрированных, дублей и немигрированных карточек  
Приоритезация: _Must have_


US-006. Как _СБ_ я хочу _ограничить доступ к критичным данным_ что бы _избежать их утечки_
Acceptance Criteria
- Предоставление согласованной группе сотрудников доступа к таблицам, содержащим чувствительные или критичные данные
- Формируемые отчеты, передаваемые за пределы согласованной группы, не содержат чувствительных и критичных данных. Проверка отчета фиксируется отметкой ответственного сотрудника СБ
Приоритезация: _Must have_


US-007. Как _бухгалтерия_ я хочу _получить отчет по отсутствующих карточках_ что бы _начислить зарплату до внесения данных в учетную систему_
Acceptance Criteria
- Получение списка по немигрированным карточкам 
- Список актуализируется по мере переноса карточек в целевую систему
Приоритезация: _Must have_


US-008. Как _администратор данных системы учета_ я хочу _провести тестовую загрузку данных_ что бы _проверить в системе учета корректность загрузки_
Acceptance Criteria
- Тестовая загрузка данных может проводиться с момента написания первых скриптов переноса данных
- Данные загружены без ошибок. 
- Данные соответствуют требованиям БД целевой системы
Приоритезация: _Should have_


US-009. Как _администратор данных системы учета_ я хочу _видеть журнал ошибок миграции данных_ что бы _исправить правила сопоставления полей БД_ 
Acceptance Criteria
- Журнал ошибок создается при каждой загрузке данных
- Журнал содержит ошибки маппинга данных или несоответствие размерности загружаемых данных в целевой системе
Приоритезация: _Must have_
