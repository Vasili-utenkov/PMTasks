### Краткая формулировка из задания: 
«Оборудование ставим к открытию офиса. Экран охраны проверяем на прототипах и меняем по отзывам».
##### Контекст и цифры
Компания переезжает в офис на 250 сотрудников. Открытие назначено на 1 сентября. До этой даты должны быть установлены турникеты и считыватели карт, а служба охраны должна видеть на одном экране гостей, сотрудников с временным пропуском и сообщения о проблеме на входе. Оборудование, поставщик и правила доступа уже выбраны договором.
Охранники проверяют прототип экрана каждую неделю. В первой версии прототипа они не заметили запись о госте и попросили сделать крупнее имя принимающего сотрудника; во второй предложили добавить понятный признак просроченного пропуска. Решения по интерфейсу ещё могут меняться, но дата открытия офиса и оборудование — нет.
##### На что обратить внимание
Стейкхолдеры.
Стабильная часть проекта — оборудование, дата запуска, базовые правила доступа. Часть, которая ещё уточняется, — удобство экрана охраны и порядок отображения информации.
Отделите выдачу пропуска, регистрацию гостя и мониторинг входа: это разные пользовательские действия.
Риски: турникет не отвечает, сотрудник потерял карту, у гостя нет приглашения, охранник не видит важную информацию на экране.
##### Выбор методологии: что проверить
Здесь одновременно есть жёсткий внешний срок и работа, которую удобно корректировать по прототипам. Подумайте, достаточно ли одного метода для обеих частей или нужен способ сочетать плановую часть с короткими проверками интерфейса.
##### Стартовые точки для User Story
Полезные роли для историй: охранник, сотрудник, офис-менеджер. Хорошее действие — увидеть статус пропуска или зарегистрировать гостя; техническая настройка турникета — не User Story.


### Шаг 2. Сбор данных. 

==тип проекта==: 
Проект разделен на 3 типа работ: 
1. Установка турникетов со считывателями карт. на них ставится ПО проверки пропусков: _внедрение_
2. Разработка ПО проверки пропусков : _с нуля_
3. Сопровождение после установки турникетов и инсталляции ПО : _сопровождение_

==состав команды==: 
_Аналитик_ - сбор требований от заказчиков (охрана, администраторы системы). Формализация требований.  Разработка технических заданий.
_Frontend_ - разработка UI. Изменения UI.
_Backend_ - разработка логики и БД. Интеграция ПО с турникетами.
_QA_ - разработка сценариев тестирования. Тестирование работы ПО по сценариям. Тестирование интеграции ПО с турникетами.
_DevOps_ - развертывание ПО на турникетах. Создание тестового стенда. настройка БД и сети.
_PM_ - руководство проектом. Координация сроков. Коммуникации с заказчиком

==уровень неопределённости==: 
_стабильная часть_: 
- Оборудование закуплено, известно API для интеграции с ним
- Сроки внедрения - 1 сентября
- Согласованы правила доступа через турникеты

_изменяемая часть_
- Изменения пользовательских интерфейсов по замечаниям
- Порядок отображения информации


==требования заказчика==: 
_Жесткие_: запуск 1 сентября. поставщик определен - заданы API для интеграции системы с турникетами.
_Гибкие_: требования к интерфейсам. Логика работы системы с данным пропусков

### Шаг 3. Выбор методологии. 

_Waterfall_: на основной поток действий: установку оборудования и инсталляцию  продукта (есть четкие сроки, определено оборудование)
_Scrum_ : на разработку ПО: короткие спринты в 1 неделю на разработку ПО до инсталляции продукта с проведением демо.
_Kanban_: сопровождение ПО в процессе эксплуатации, без откладывания решения возникшего инцидента в ближайший незапланированный спринт

_точка синхронизации_: к 1 сентября ПО должно быть развернуто на установленном оборудовании.

### Шаг 4. Инициация проекта. 

==Название и описание проекта==

_Установка системы доступа по пропускам в новом офисе_
1 сентября компания переезжает в новый офис на 250 сотрудников. До этой даты необходимо установить систему доступа в здание по пропускам. Система включает в себя турникеты, считыватели карт и программное обеспечение для работы с пропусками, основным элементом которого является монитор отображения состояния пропуска, расположенный на посту охраны. Цель - обеспечить контролируемый доступ в здание офиса сотрудников и гостей с момента его открытия.


==Цели проекта==
- До 1 сентября во всех точках входа в здание установить и ввести в эксплуатацию систему доступа, рассчитанную на обработку 250+ действующих пропусков, обеспечив на 100% функциональность программно-аппаратного комплекса. Проверяется актом приемосдаточных работ.
- Достичь отсутствия критических инцидентов(не отображает данные пропуска, не пропускает сотрудника по валидному пропуску) в первую неделю эксплуатации - не более 1 инцидента в день, фиксируемого в журнале поддержки

==Ограничения и допущения==
_Ограничения_: 
- Дата открытия офиса 1 сентября
- Определен поставщик и оборудование. Технические характеристики оборудования не меняются.
- Определены права доступа

_Допущения_:
- Дата переезда не изменится на более раннюю
- Оборудование и инфраструктура будет установлена и налажена к проведению пусконаладочных работ
- У охраны будет возможность регулярно тестировать прототипы и давать обратную связь
- После 1 сентября ПО будет сопровождаться командой разработчиков


==Критерии успеха==
- К 1 сентября система установлена и успешно протестирована по тест-кейсам. Результаты тестирования занесены в акт приемосдаточных работ. 
- В период опытной эксплуатации отсутствуют критические инциденты, блокирующие проход в офис
- Время отклика системы меньше 0.5 секунд
- Монитор на посту охраны отображает в реальном времени данные пропуска и сообщения о проблемах на входе
